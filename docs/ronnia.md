# RonniaBot et la file Ritsu

Étude statique du service hébergé. Les sources épinglées sont [le bot Python](https://github.com/aticie/ronnia/tree/ddc182c7d1414a3f1b97b12a800ff5fd09a77ba8) et [le tableau de bord](https://github.com/aticie/ronnia-web/tree/44fc9802f9fd6ea30b32e0e5991304843178e5cf). La branche de migration contient [le backend Rust](https://github.com/aticie/ronnia/tree/4d008d18e09d12e910f2f3cdf40f36a684f1f06e), également examiné. Les révisions effectivement déployées et le parcours avec un compte réel restent à confirmer.

## Parcours vérifié dans le code public

1. Le tableau de bord propose deux autorisations distinctes, Twitch et osu!. Elles peuvent être données dans les deux ordres. La branche Rust demande `identify` côté osu! et `channel:bot` côté Twitch. Ce dernier consentement active le bot sur la chaîne liée. [Déclaration des scopes](https://github.com/aticie/ronnia/blob/4d008d18e09d12e910f2f3cdf40f36a684f1f06e/src/api/oauth.rs#L53) La session et les identifiants du fournisseur sont gérés côté serveur. Le code du tableau de bord montre les routes de connexion, de session, de réglages et de migration. [Parcours de connexion](https://github.com/aticie/ronnia-web/blob/44fc9802f9fd6ea30b32e0e5991304843178e5cf/README.md) · [Client HTTP du tableau de bord](https://github.com/aticie/ronnia-web/blob/44fc9802f9fd6ea30b32e0e5991304843178e5cf/src/api.ts)
2. Le bot rejoint les chaînes Twitch détectées en direct. Il analyse les liens envoyés dans le chat, résout une difficulté via son cache ou l’API osu!, puis applique les règles de demande. La documentation publique mentionne le stream actif et osu! en cours de jeu. Dans la branche Rust, la porte de présence dépend du direct et de la catégorie osu! du stream. Vérifier le comportement déployé avec lazer et Ritsu selon le statut de migration. [Contrôle Rust de la demande](https://github.com/aticie/ronnia/blob/4d008d18e09d12e910f2f3cdf40f36a684f1f06e/src/bot.rs#L912) [Gestionnaire des demandes Twitch](https://github.com/aticie/ronnia/blob/ddc182c7d1414a3f1b97b12a800ff5fd09a77ba8/ronnia/bots/twitch_bot.py)
3. La révision Python prépare un message contenant un lien de difficulté en forme `osu.ppy.sh/b/<id>`, le titre et des détails de demande. Elle utilise l’API v2 `POST /chat/new` avec le scope délégué `chat.write` pour livrer le message privé. Le README et des noms internes décrivent historiquement IRC. Le mode de migration comporte aussi un appel interne authentifié de réservation et de rapport de livraison. L’ID numérique réel de l’expéditeur hébergé doit être relevé sur un message de test. [Construction du message et livraison](https://github.com/aticie/ronnia/blob/ddc182c7d1414a3f1b97b12a800ff5fd09a77ba8/ronnia/bots/twitch_bot.py#L602) · [Client chat osu!](https://github.com/aticie/ronnia/blob/ddc182c7d1414a3f1b97b12a800ff5fd09a77ba8/ronnia/clients/osu.py#L198)

## Réception depuis un client tiers

L’API osu! documente la lecture des messages via OAuth avec un utilisateur et `chat.read`. Elle réserve les scopes chat à un compte bot agissant pour d’autres utilisateurs ou à un grant dont l’utilisateur est le propriétaire de l’application. `chat.read` est non délégable. Une liaison dans le tableau de bord Ronnia ne confère donc pas de droit de lecture à Ritsu. Les routes publiques Rust exposent notamment des classements agrégés de maps demandées. Leur contrat ne fournit ni flux ni historique individuel exploitable par une file tierce. [Routes Rust](https://github.com/aticie/ronnia/blob/4d008d18e09d12e910f2f3cdf40f36a684f1f06e/src/api.rs#L54) Les routes internes du pont de migration sont destinées à leur propre déploiement. [Scopes OAuth](https://osu.ppy.sh/docs/#scopes) · [Lecture des messages](https://osu.ppy.sh/docs/#get-channel-messages)

Si une source publique et autorisée devient disponible, extraire l’ID de difficulté du lien après validation de l’expéditeur par ID et du domaine. Résoudre les difficultés importées via `BeatmapInfo.OnlineID`, puis reprendre leur MD5 local pour la file. Une map absente ou plusieurs correspondances nécessitent une décision explicite du joueur. Dédupliquer les livraisons par ID de message et les entrées actives par MD5. Un lien vers un set seul ne suffit pas à sélectionner une difficulté.

Pour conclure sur un jalon réseau, vérifier avec un compte dédié les deux autorisations, la présence avec un client de référence, l’identité et le format du PM reçu, un événement répété et une demande vers une map absente. Confirmer auprès de l’opérateur l’existence et le contrat d’une interface tierce avant d’ajouter une intégration au client.
